08Context engineering & memory

"What does the agent know, see and remember at the moment of action?" The discipline that separates a demo from a dependable system.

🗒 Short-term (scratchpad)

Run-scoped state checkpointed across every step — write a fact now, fetch it later. When the window fills, old context is compacted into a summary (this build was compacted mid-run and resumed without losing the thread).

🧠 Long-term memory

Knowledge that survives the session — stored as files with per-write audit trails, shareable between agents. One run learns from the last instead of starting cold (e.g. created-record IDs, prior decisions).

🛠 Tools as context

Tools consume the context budget too. The model gets context-awareness (how much budget remains), prefers programmatic tool-calling for fan-out, and relies on crisp tool descriptions — it only acts as well as its tools are described.

Rule of thumb: curate context, don't dump it. Retrieve the few facts a step needs, summarise the rest, keep tool outputs tight. Most agent failures are context failures — wrong, missing or stale information at the moment of action.

09RAG — grounding the engine in real facts

Retrieval-Augmented Generation feeds the model real, current information (the company's docs, rates, photos, the live web) rather than trusting memory. The Research agent grounds every written claim and carries a source + confidence with it.

Governance precedes retrieval. Access controls, metadata and provenance come first; every claim carries source + confidence, and the engine never invents what it can't retrieve — which is why the report flags unverified items explicitly.

10Guardrails, security & human-in-the-loop

🚦 Gated & bounded

No stage starts before the prior verifies green. Retries are bounded (max attempts) then escalate — no thrashing, no runaway cost.

🙋 Human approval

Price changes, destructive resets and outbound guest comms pause for explicit sign-off. Info-only steps run automatically.

🔒 Secrets & least privilege

Credentials are runtime config, never committed; tools run least-privilege; keys rotated after use; external/retrieved content treated as untrusted (prompt-injection defense).

🔁 Idempotent writes

Search-by-natural-key before every create — re-running a stage never duplicates records.

🧾 Audit trail

Every write logged; created-record IDs persisted so partial progress is detectable and resumable.

✅ Validation

Inputs validated and typed at the tool boundary; outputs checked against schema and target counts.

14How to run it

Driven inside Claude Code: background Agent tasks for each specialist, the /loop skill for verification cadence, and an Odoo MCP server (or XML-RPC) for the build.

1 · Connect

Attach the Odoo MCP / credentials + the Google Drive connector. Hand the Orchestrator the brief, company name & personnel.

2 · Dispatch & loop

Orchestrator launches stage agents; /loop re-runs each stage's verification and advances only on green.

3 · Approve & ship

Approve the gated steps (pricing, comms, resets); the engine commits, deploys and leaves the Odoo demo live.
